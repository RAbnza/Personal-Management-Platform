## 1. Purpose, authority, and scope

Replace the accumulated page-and-panel interface with a coherent personal application: quick to enter, easy to navigate, precise about financial meaning, and comfortable for daily use. This is a structural redesign of navigation, composition, task flows, presentation, and interaction. Preserve every implemented V1–V3 capability, including less frequent correction, archival, recovery, and permission-sensitive workflows.

This document is the owner-approved redesign specification as of October 17, 2026. It takes precedence over superseded visual, navigation, geometry, palette-role, typography and density recommendations in the existing design guidelines. The current UI remains the implemented baseline until separately assigned milestones change it; approval does not supersede product, financial, security, persistence, API or historical behavior. Where the plan is silent, retain the existing contract. Later implementation must explicitly record any newly discovered conflict instead of silently changing behavior.

## 2. Current UI/UX assessment

The strongest foundation is behavioral: the repository already protects difficult financial and privacy cases and supplies extensive acceptance evidence. The weakest area is how these capabilities are arranged and explained. The redesign should preserve those protections while replacing the repeated long-page composition.

### 3.1 Capability limits that the redesign must tell the truth about

- Sharing is fully implemented but `SHARED_EXPENSES_ENABLED` defaults false; the legacy preview is local/test-only. Preserve deployment gating and existing authorization. Never advertise or activate Sharing solely because a navigation design includes it.
- Trackers are normally available, with an operational disable. Module visibility, Agenda visibility and reminder preferences remain independent.
- Calendar currently implements Agenda, not an installed FullCalendar month/week scheduler. A date navigator must not imply complete month data from one 50-item page.
- No installed global record-search engine, persistent customizable dashboard, Career drag board, formulas, habit streaks, external calendar synchronization or multi-currency financial conversion is established by this audit.
- Financial workspace currency remains PHP. Career salary currency is a different field. A preference redesign must not imply financial currency conversion.
- Report CSV is not a complete backup. Current portable graph exports exclude attachment bytes and shared-group authority. Current replacement/recovery rules are more constrained than “import any backup.”
- Automated invitation email is not an advertised current capability. Secure manual invitation handoff and existing explicit notification consent remain the current behavior.

**Synthesis:** a warm, precise personal workspace with a compact application frame, violet actions, charcoal focal surfaces where useful, restrained teal/amber accents, strongly aligned records, and contextual detail. Personality comes from composition, typography and purposeful color; important data stays on opaque quiet surfaces.

Rejected directions: a uniform wall of rounded metric cards; a giant marketing greeting; orange gradient branding copied from Reference 3; a permanently icon-only dock; automatic removal of all side panels; unsupported AI recommendations; animation as a prerequisite for reading or acting.

### 6.3 Lists, search, filters, sorting and pagination

- Use semantic tables for comparisons; use compact labeled rows on small screens. Do not duplicate two active DOM views. Essential mobile fields are title, amount/status, date, owner/scope or account as applicable, and a detail action.
- Keep the current endpoint's filtering, ordering, cursor/offset and limit contracts. TanStack Table supplies view state; it does not create missing server capabilities. Never sort/filter one loaded page and label it the entire dataset.
- Expose only supported sort fields. A fixed-order source says “Newest first” or its actual order and has no inactive fake sort control. New backend search/sort requires a separate explicitly scoped task, not an implicit redesign dependency.
- Existing search on Career and tracker entries remains available. Preserve query privacy rules; do not put financial notes, contact details, invitation tokens, amounts or form payloads into new URL state. Do not broaden existing text-in-URL exposure.
- Show active filters, a clear/reset action and an empty-filter state distinct from an empty collection. Apply expensive multi-filter changes explicitly; use small search debouncing only where the current read contract supports it.
- Cursor sources use Next/First and a session-held Previous cursor only if safely implemented. Do not invent page counts or arbitrary “page 12.” Offset sources retain actual offset semantics. Announce the visible result range only when known.
- Preserve independent cursors on multi-list pages (templates/trackers, reservations/history, installment candidates/applications). A subsection change must not accidentally reset another review's selected entries.
- No default infinite scrolling, automatic bulk selection across unseen pages, or virtualization. Keep existing bounded pages; evaluate virtualization only if measured DOM cost warrants it.

## 7. Screen-by-screen redesign specifications

The inventory in Section 3 defines route coverage. The following recipes define what the user sees and does. All inherit the accessible states, exact-value rules, responsive behavior and command protocol in Section 6. Do not interpret local section names as permission to add new entities or services.

### 7.1 Home and spending drilldown — HO1, HO2

**Purpose:** answer “What needs attention, what is coming next, and where do I start?”

- Header: compact greeting/date, current workspace scope, contextual Add. No full-width promotional hero.
- First region: attention queue ordered by the existing service priority, with due state, source, short reason and direct action. Keep all existing items accessible; show a compact first set with “Show all attention items,” not an arbitrary silent cut.
- Second region: Today/Upcoming Agenda beside a concise current snapshot. Current balances and period-based spending have separate labels and time contexts. Display at most three prominent metrics; the remaining current metrics and coverage remain in a named “Financial details” region with a visible opening control.
- Third region: Career and tracker progress summaries followed by recent activity. Budget, goal and card details remain accessible in compact expandable sections and domain links, retaining the actual fetched evidence. No new dashboard customization persistence.
- Place quick actions near the opening content, rather than below every report. Show Getting started as one compact next-step card; its full checklist opens separately.
- On mobile: attention → actions → upcoming → snapshot → progress → activity. When no records exist, show the relevant first action and an explanation of unknown coverage, not zero-valued charts.
- Preserve financial records in summaries when Money is hidden as required by the current contract; show the existing hidden-module explanation in concise form. Do not silently redefine financial scope for visual simplicity.
- Spending drilldown keeps the exact selected dates/filter semantics and links to logical actions. The back link restores Home context. Negative net spending after refunds must remain visible.

### 7.2 Access, setup, Settings and Help — AU1, AU2, ON1, ST1, ST2, HP1

Access screens use a centered 440px form on desktop and a full-height compact layout on mobile. Keep password-manager/autofill support, validation and generic email outcomes. A verification/recovery status screen states the next action and whether the link is invalid or expired without exposing account existence. Preserve safe return destinations and current session revocation behavior.

Current setup remains online-account based. Present the existing starting goal and preferences first, then the next useful real action. Career-only setup bypasses Money. Optional steps can be skipped; progress is resumable; viewing Help or an example does not complete a financial action. PHP is shown as the current financial currency, not an editable conversion promise. The full checklist remains accessible from More and Home.

Settings uses a category list and a focused content panel on desktop; mobile opens one category at a time with Back. Preserve profile, theme, timezone/week start, module visibility, Agenda visibility and all existing preferences. Module toggles explain the independent consequences and show retained history. Theme changes use the current preference version and pending/error feedback.

Security shows current session first, then other sessions with available device/time details and individual/all revocation. Password change/recent-authentication tasks are focused forms. Do not invent biometric, device-lock or local PIN controls in current V3.

Help uses task names: “Record a transfer with a fee,” “Correct a transaction,” “Review a shared payment,” “Update a tracker template.” Include search over static guide titles/text only if implemented locally without private data indexing. Preserve replayable tours and the support draft flow. Diagnostics are previewed and chosen by the user; no automatic support transmission.

### 7.3 Accounts and reconciliation — MO1–MO3

Accounts default to aligned rows: name/type, current balance, cutoff/coverage and existing lifecycle state. Add account opens a dedicated form presentation instead of permanently occupying the list. Explain opening balance directly beside its date/amount: “Balance already held on this date.” It is not income. Preserve all existing opening/current balance and negative-balance behavior.

Account detail has a compact balance header and Activity/Reconciliation history sections. Activity shows date, description, kind, signed cash effect and available balance/history evidence. A transaction row opens action detail; it does not edit ledger postings inline. Preserve supported filters and pagination.

Reconciliation is three steps in one task: enter observed balance/date → compare with recorded balance → choose the existing explicit adjustment/review action if needed. Display observed, recorded and difference in aligned columns, then relevant transactions. A match shows “Matches”; a mismatch never triggers an automatic adjustment. Preserve exact equity classification and historical evidence. Mobile stacks the three labeled values above the transaction list.

### 7.4 Income, expense and transfer entry — MO4, MO5

Use a task title and source context rather than a generic “Add” modal. The form's essential fields come first: amount, date, funding/destination and description. Income and expense remain distinct intents; a receipt is not automatically income. Preserve all existing sender/source, merchant, reference, notes and classification fields in meaningful groups.

Expense funding explicitly chooses cash account or credit card. Card selection reveals provider posting/reference fields and preserves purchase recognition semantics. Category splits show exact total and remaining-to-allocate. Fees have their existing treatment/bearer fields and visible cash consequences. Recurring occurrence linkage stays identifiable before confirmation.

“Shared expense” reveals the existing integrated group/payer/share flow. Inline group creation preserves entered amount, categories and funding intent; it must not discard the outer form. Group and private effects are reviewed separately. Capability gating and participant authority remain unchanged.

Transfer uses “From,” “To,” principal sent/received and separate fees. The review distinguishes own money movement from spending. Never show principal transfer as income. Preserve negative-balance acknowledgements and actual fee treatment.

Funding or destination             Spending: recognized effect
Description / category             Liability: change where applicable

### 7.5 Financial activity, corrections and refunds — MO6, MO7

Activity is the Money landing view. Use current logical actions as list rows; correction revisions do not create duplicate apparent purchases. Keep funding/card filters supported by the source. The detail header shows actual effective date, action type and exact total with an explicit cash/spending/liability interpretation.

Sections: Overview, History and Files; linked debt/card/recurring/group evidence is discoverable within Overview. More actions offers only supported operations for the current action. Rename technical enums in visible copy while preserving payload values.

Correction starts with the original and replacement side by side on desktop, stacked with explicit labels on mobile. Preserve all required fields, reason, expected revision, negative cash acknowledgement and special linked-source restrictions. Refund selects the actual eligible original portions and receiving/card effect, not a free-floating negative expense. Clearing resolution explains what was unknown and what evidence now resolves it; it does not deduct the original cash again. Reversal shows exact consequences and history retention. Shared-source conflicts link to the existing private reconciliation flow rather than forcing an ordinary correction.

### 7.6 Debts — DE1–DE4

Debt list columns: name/lifecycle, recognized balance, next supplied due date/amount, overdue/unknown status. Do not combine recognized liability and remaining schedule into one headline total. No donut implying repayment completion if original principal/history is missing.

New borrowing and Import existing debt remain separate entry choices. Borrowing prioritizes actual cash received and recognized liability/fees. Import prioritizes cutoff, remaining liability, supplied paid/unpaid schedule history and uncertainty. Keep unknown breakdowns unknown; optional evidence is expandable, but any unresolved consequences stay visible in Review.

Debt detail: Overview shows recognized balance, contractual remaining payable and next due as separate facts. Schedule shows due items and satisfaction; History retains payment, schedule and settlement evidence with effective/recorded dates. Contextual actions are Pay, Revise schedule and Settle.

Payment task separates **what the payment represents** (principal/known charges/clearing/advance) from **which contractual dues it satisfies**. A compact review presents both axes, actual account cash and external fee. Preserve explicit unapplied amounts and unknown schedules; do not infer principal from cash.

Schedule revision compares old/new dues and remapped satisfaction. Paid history remains inspectable. Settlement distinguishes cash paid, recognized reduction/waiver, avoided future charges and remaining unresolved amounts. Show blocking reasons before confirmation; never offer “mark settled anyway.”

### 7.7 Cards, statements and installments — CC1–CC6

Card collection uses restrained account-like tiles/rows with issuer/name, recognized outstanding, available-credit evidence/unknown state and next verified due. Do not mimic bank connectivity, display fake full card numbers, or present available credit as personal cash.

Card detail: Overview, Activity, Statements, Installments; management fields open through Edit card. Show recognized balance, statement payable, provider limit/available-credit information and credit/overpayment state separately. Archive is reversible and does not erase liabilities or history.

Record payment/charge chooses a supported action explicitly. Card payment names the paying cash account; fees/interest/refunds show their distinct effects. Keep original purchase selection, allocation and reversal functionality and pending/retry states.

Statements use a comparison composition: provider evidence on one side, tracked evidence on the other, difference/reconciliation state below. Add/revise statement uses an evidence form with candidate transactions and existing 100-item candidate pagination. Allocations are a separate task with exact remaining amount. Correcting statement evidence never becomes a financial posting.

Installment detail uses a schedule table, current provider evidence, application links and immutable history. Explicit applications connect to statements through existing controls. Preserve cancellation/revision and suspended projection states after source purchase changes; do not infer that a reversed purchase automatically cancels a provider plan. On mobile, due rows show date, amount, application/state and an expandable evidence line.

### 7.8 Recurring obligations, budgets and goals — PL1–PL3

**Recurring:** browse definitions with next expected date and state. Create/edit uses frequency/interval/end controls and a readable preview, including the existing shorter-month rule. **Budgets:** show category, period, exact limit, signed actual spending and remaining/overspend. Use a horizontal comparison bar with a visible over-budget portion; preserve negative actuals rather than forcing a zero floor. Detail separates definition/history from source contributions. Conflicting periods and archived states have clear corrective actions. No rollover, cash reservation or category aggregation changes are introduced.

**Savings goals:** show target, recorded reservation and currently supported funding as different values. For shared account shortfalls, use the service's existing supported bounds, not an invented per-goal allocation. Detail shows account reservations, global availability constraints and history. Reserve/release/reallocate/complete/reopen/archive are focused existing commands. Label every reservation task “does not move money.” Shortfalls remain visible even when a nominal target is reached.

### 7.9 Forecasts — PL4

Desktop: assumption panel (bounded width) beside results; mobile: Assumptions and Results sections with retained in-memory inputs. ### 7.10 Career — CR1, CR2

Applications use company/role, current stage, outcome, applied date and next scheduled action as the scan hierarchy. Retain search/stage filtering and cursor pagination. Saved opportunities are visibly different from submitted attempts. Do not add a board dependency or assume one company equals one application.

New application groups basics first, then job details, salary/contact, role snapshot/resume reference and notes as meaningful optional sections. Preserve all fields and duplicate warning with a deliberate Continue choice. No automatic fetching of posting URLs.

Stage transition uses a controlled form with existing validation; it never fabricates an interview. Repeated/skipped stages and reopened attempts remain valid. Archived applications retain evidence and existing mutation restrictions. Mobile event forms use an explicit date/time/timezone summary before confirmation.

### 7.11 Calendar and reminders — TM1–TM3

Calendar opens to Agenda, with Today, previous/next bounded range, dates and source filter near the list. Date groups contain source icon/label, title, date or time, due/completed/cancelled state and source action. A narrow desktop date navigator is useful, but contains no fabricated event density dots. Preserve pagination and the explicit end-of-range state.

Reminder attention becomes a compact region with count and review link rather than a large instructional panel before the Agenda. Existing module defaults remain reachable from Calendar and notification settings navigation. Do not invent a missing tracker-default control without checking the actual endpoint/UI contract; entry-level tracker reminders remain required.

Month/week calendar views are an optional later presentation enhancement, not required for completing this redesign. FullCalendar is evaluated in Section 9, but installing it or altering range APIs is not on the six-milestone critical path.

### 7.12 Trackers and entries — TR1, TR2

My trackers shows name, template/version, available progress/deadline metadata and archive state. Do not fetch every entry just to paint a tile. Preset creation presents Learning, Books and Personal Tasks with short field previews. No spreadsheet editing that bypasses immutable revisions. ### 7.13 Templates and migration — TR3, TR4

Template editor is a workspace, not a large form embedded beneath version history. Desktop: field list → selected field settings → compact preview. Mobile: field list → full-screen field settings → preview. Use explicit Move up/Move down controls for ordering; drag is unnecessary. Retain all allowed types, defaults, bounds, required/retired states, select options/retirement, and title/status/deadline/completion mappings. Stable identifiers are read-only explanatory metadata, not casual editable labels.

Publish review shows definition changes, affected interpretation and the fact that existing trackers do not automatically update. Existing fields/options are retired under the current rules; do not offer destructive field deletion. Current editor drafts are in-memory only; label unsaved changes honestly and warn on leaving.

Migration is a guided task:

```text
Choose target version → Map fields/options/defaults/conversions
→ Review valid/invalid counts + before/after samples
→ Fix invalid data/mapping and prepare a fresh preview if needed
→ Confirm the reviewed plan → Process bounded batches
→ Completed, or Partial/Cancelled with explicit Resume
```

Show the exact target, reviewed mappings, total/valid/invalid counts, first 50 invalid-entry links and up to five samples. Label those limits; do not call samples the full dataset. Progress derives from confirmed server counts. Each command processes at most 50 entries; browser automation must not imply a background worker will continue after closing unless the actual contract supports it. Cancel retains committed batches; partial plans retain locks; the tracker switches version only after all required entries, including archived entries, resolve. A restored cancelled partial plan offers Resume with a fresh state read, not a promise of rollback.

### 7.14 Shared expenses and private integration — SH1–SH4

Shared expenses has its own clearly labeled scope. Group list shows name, membership/state and available balance summary. Invitations is always discoverable when the capability is enabled. Joining shows group identity, proposed membership/manual-person claim, privacy explanation and explicit consent. Invalid, expired, revoked, already-used or unauthorized invitations receive safe recovery text without exposing unrelated group data.

Group workspace uses Overview, Bills, Payments and People. Overview shows confirmed net positions; pending projections are a separate labeled comparison. Person detail explains the relationship through bills, refunds and confirmed settlements. Suggestions are explainable proposals, not executed transfers. Preserve indirect-discharge restrictions and the existing explicit-bill/direct-settlement fallback.

Bill entry separates **Who paid?** from **Who shares the cost?** Multiple payer contributions and selected equal/exact shares each total exactly to the bill. Show deterministic rounding results before confirmation. Refund and revision views retain before/after evidence and private adoption mismatch warnings. Group spending and the user's private recognized spending are not interchangeable totals.

Payments presents Needs my confirmation, Waiting for others and History filters. Reporting a payment asks full relationship/custom amount/selected bill allocations and handles partial/multi-bill/advance cases. Recipient confirmation, manual confirmation, disputes, cancellation and reversal retain their actual actor rules. A pending or disputed report never reduces the confirmed balance. Do not phrase a record-only action as “Send money.”

People contains registered/manual identity labels, roles, invitations, exit/removal and archive controls. Show authorized actions only, with recent-authentication steps when already required. Former-member views explicitly say Historical access and show only entitled evidence.

My private record is visually marked Private and explains that adopting/reconciling a group source affects only the current user's records. Separate Record cash, Link existing purchase, unpaid-share adoption, settlement/refund/clearing and retained-evidence review as the actual source allows. Show accepted/current source revision and stale mismatch. No group edit may silently rewrite someone else's ledger. Authorized group-history JSON remains downloadable and clearly non-restorable; omit private funding and invitation contacts/tokens as the current export does.

### 7.15 Reports and tracker statistics — RP1, TR5

Reports provides Financial, Career and Trackers destinations with a compact period toolbar. Keep each report's own legitimate filters and date limits. Shared period styling does not imply identical metric definitions or merging unrelated APIs. Existing `/reports` default remains Financial.

Financial report starts with labeled income/spending/cash/liability measures, then a meaningful visualization and the exact data table. Drilldowns carry the same scope and dates. Coverage, cutoffs, currency, timezone, generated time and calculation provenance remain accessible; material uncertainty is inline. CSV matches the selected report and retains existing formula-safe encoding and bounds.

Career report clearly names submission cohort and as-of date. Separate milestone progression, completed transitions, time in stage, source comparison and upcoming operational counts. Empty denominators say Not applicable. Do not introduce a funnel that assumes every application followed the same stages.

Tracker report separates **Current state** from **Recorded activity in this period**. Display completion eligibility and excluded definitions, version coverage and current archive-filter meaning. A manually entered completion date is not a recorded transition. Migration activity is distinct from user edits. Preserve 366-day interactive bounds and current report/CSV limits (10,000 entries / 20,000 activity revisions). Ineligible progress never appears as 0% completion.

### 7.16 Notifications, files, data and lifecycle — ST3–ST6

**Notifications:** show consent/channel controls, privacy settings and timezone/quiet hours first. Delivery evidence is a separate list: scheduled, attempted/uncertain, accepted, delivered or other actual outcome. Accepted is not delivered/read. Required security email is separate from optional reminders; hiding a module does not revoke consent. Preserve current opt-in and freshness checks. Do not add unimplemented push registration.

**Files:** desktop catalog table/mobile rows with file name/type, source, size, scan/availability state and permitted actions. Upload shows accepted types/limits before selection; quarantine and unavailable-restored-file metadata have distinct labels. Download only through existing authorization/scan checks. Keep all eight supported source associations accessible centrally and existing contextual attachments. Deletion requires actual acknowledged behavior; never show an optimistic irreversible success.

**Data:** first screen presents four explicit tasks: Import CSV, Export workspace, Replace workspace, Recover a replacement. CSV uses choose account/format/date/cutoff → preview/mapping/duplicates → select/acknowledge → process batches → outcome. Preserve 1 MiB/500-row input limits and 50-row chunks. Cancelling does not reverse imported rows; retry reuses durable row commands. Historical rebase remains a specific reviewed capability, not a generic overwrite checkbox.

Export states contents, exclusions and artifact expiry. Replacement compares current/replacement counts and exact totals, provenance and blockers, then uses the existing typed confirmation. Retain the 10 MiB/10,000-total-row graph limit, attachment-byte exclusion, live-file protection, trusted own shared history, external-attempt restrictions, notification-consent reset and 24-hour recovery graph. Show recovery expiry and Download/Reapply choices. Restored tracker migration locks and unavailable file bytes must remain understandable. Do not use the word “backup” for a graph export without its limitations.

**Account/data deletion:** isolated page with exact scope, retained shared evidence/backup limitations, recent authentication and explicit confirmation. Pending deletion has a clear deadline/cancel action during the current grace policy and limited authorized access. Do not place destructive controls beside routine theme settings or promise immediate erasure of every backup. Maintain other users' and authorized shared history according to current lifecycle rules.

## 11. Motion and microinteractions

**CURRENT REDESIGN + FUTURE-READY FOUNDATION.** Motion communicates input response, containment and state change. It must not delay availability, imply save completion, or distract from reading values.

| Interaction               | Duration / easing                                                           | Behavior                                                                      |
| ------------------------- | --------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| Hover/focus/pressed color | 100–140ms, `cubic-bezier(.2,0,0,1)`                                         | Stable geometry; focus outline appears immediately                            |
| Menu/help popover         | 120–160ms enter, 100–120ms exit                                             | Opacity and at most 4px translation; no bounce                                |
| Detail panel/small sheet  | 180–220ms, `cubic-bezier(.2,0,0,1)`                                         | Short contained transition, focus delivered when ready; no long screen travel |
| Disclosure                | 140–180ms                                                                   | No animated hundreds-of-row layout; opening content remains readable          |
| Route change              | Optional 100–140ms content fade                                             | Frame stays stable; no artificial wait or animation of the whole application  |
| Save result               | Brief status/icon change                                                    | Only after authoritative confirmation; no confetti or rolling money counters  |
| Chart update              | 0–180ms for small visual transitions                                        | Exact labels immediate; large data or reduced motion uses no animation        |
| Loading                   | Stable skeleton after a brief delay for real waits; text status immediately | Match eventual layout; avoid flicker and endless shimmer                      |

Use transform/opacity where possible and avoid layout measurement loops, large filters and moving backgrounds. A press can change fill; do not scale financial text or move a pointer target away from the user. Prefer CSS with existing primitive states. If Motion is justified, lazy-load its use locally and prove the complete route cost.

`prefers-reduced-motion` removes translations, animated height/layout, skeleton shimmer, chart interpolation and decorative movement. Use immediate state changes or a short opacity change only when comfortable. Follow OS settings, avoid whole-page theme transitions, and stop nonessential animation in background tabs. A reduced-motion user receives every status and result.

## 12. Accessibility, performance and platform behavior

### 12.1 Accessibility acceptance standard

Target WCAG 2.2 AA for the current web interface. Preserve the existing 320px reflow baseline and add actual keyboard/screen-reader verification of new patterns. Automated axe results alone are insufficient.

- One visible main landmark/page heading; a working skip link; clear hierarchical headings and page titles. No hidden retained page can contain active duplicate controls or steal focus.
- Logical Tab order; arrow-key behavior only for appropriate composite widgets; native links/buttons for navigation/actions. No unmodified single-letter global shortcuts or keyboard-only feature.
- Focus enters a dialog meaningfully, remains contained if modal, and returns to its trigger. Confirmation dialogs focus a safe initial action. Route changes focus the new heading without disrupting ordinary in-page edits.
- Normal text at least 4.5:1; qualifying large text at least 3:1; essential controls/indicators distinguishable at 3:1 in actual states. Status includes text/icon and is not hue-only.
- Default touch targets 48px, web default controls at least 44px. These are product targets stronger than WCAG's 24px minimum/spacing rule ([W3C target size](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)). No tiny icon hit areas or overlapping expanded targets.
- At 320px and 200%/400% zoom, primary content and actions remain available. Tables can have a labeled contained horizontal region only where a two-dimensional comparison truly requires it; the whole page cannot scroll sideways.
- Sticky headers, bottom docks, sheets and the software keyboard must not hide focused controls ([W3C focus not obscured](https://www.w3.org/WAI/WCAG22/Understanding/focus-not-obscured-minimum.html)). Test portrait, landscape and large text.
- Errors are associated with fields and summarized; focus the first invalid field or summary as appropriate. Live regions announce meaningful save/progress changes once, not every rerender or row.
- All charts have exact accessible tables and summaries. All information available on hover is available by focus and touch. No drag/swipe-only operation.
- Honor forced colors, reduced motion, OS text scaling, text selection, password managers and browser autofill. Never block paste into passwords or confirmation fields without an existing justified security contract.
- Verify NVDA or Narrator with Windows browser and TalkBack with Android browser for representative current flows. Future native clients require their own platform accessibility verification.

### 12.2 Performance requirements

Measure against an M1 baseline, not an imagined package-size estimate. Use the existing synthetic household profile (10,000 financial actions, 1,000 applications/events and the documented shared-expense fixture) and retain the optional larger profile for justified investigations. Do not reset existing test budgets to hide a regression.

| Requirement          | Target / verification                                                                                                                                                                            |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Interaction feedback | Visible response to press/submit within 100ms where practical; show real pending state while waiting                                                                                             |
| Mobile usability     | Existing primary content target under 3s on a representative network/device; document exact device/throttling used                                                                               |
| Server behavior      | Preserve architecture targets: common reads p95 <800ms, financial commands p95 <1s, Dashboard/ordinary reports p95 <2s under the relevant local fixture; these are targets, not new measurements |
| Client cost          | Record compressed route JavaScript, hydration and interaction timings before/after; no unexplained increase over 10% for representative routes without explicit rationale and measurement        |
| Layout stability     | Reserve chart/loading dimensions; no navigation jump when capability data resolves; target CLS ≤0.1 and responsive interactions, measured rather than claimed                                    |
| Low-end behavior     | Representative browser run at 4× CPU throttling plus one real midrange Android device when available; basic tasks remain usable if optional chart/motion code loads late                         |
| Data work            | Current server pagination/bounds; no all-record client fetch for sorting, global search or dashboard decoration; avoid new N+1 requests                                                          |
| Private caching      | No persisted private query cache, no cross-user query reuse, no service-worker data cache introduced by redesign                                                                                 |

Do not rerun full database restoration or infrastructure campaigns after every visual change. Use impact-based checks per milestone and one consolidated acceptance phase. If a UI change exposes a service/API defect, record it and obtain a properly scoped implementation decision rather than quietly redesigning the backend.

## 13. Future Offline-First Windows and Android UX

Everything in this section is **FUTURE MIGRATION** and, where architecture is involved, **PROVISIONAL / UNRESOLVED**. It is conceptual planning, not current V3 implementation scope. None of decisions F01–F07 blocks M1–M6. Current authentication, online writes, data protection and failure behavior remain intact until a separately approved migration.

### 13.1 Proposed first-launch and returning-user journeys

**New installation without local data:** Welcome → Create local profile → confirm minimal preferences → enter Home. Optional guided first action follows inside the application. Restore existing data is an equally clear secondary route from Welcome. Avoid an account-registration prerequisite for personal tracking.

1. **Welcome:** brief description of Money, Career, Calendar and Trackers, a primary “Create a local profile,” and “Restore existing data.” State that collaboration may require online identity later. No decorative carousel or forced tour.
2. **Profile:** required display name only by default; optional avatar/color. Explain “This profile's data is stored on this device” only if the chosen architecture actually guarantees that scope. Do not claim encryption, backup or recovery protection merely because data is local.
3. **Preferences:** suggest device timezone, existing supported currency policy and week start; choose starting goal. Keep financial currency read-only unless a future product decision explicitly expands it. Notification permission is requested when enabling a useful reminder, not before the person understands the application.
4. **Home:** one suggested first action, optional checklist, and a concise data-safety prompt leading to backup settings. Skip leads directly to useful work; no automatic sample financial records.

**Returning single-profile user:** open their last safe work area or Home; require local unlock only if configured and supported. Revalidate stored state before presenting confirmed balances. Never show a previous profile while another opens.

**Multiple profiles, if approved:** show a profile chooser before entry or through Account → Switch profile. Do not treat a display name switch as a security boundary. Each profile's data, drafts and cached views must be isolated according to the future architecture. Unfinished local creation returns to a recoverable setup state with a clear retry/delete-incomplete choice; atomicity belongs to the future implementation.

**Existing data / upgrade:** detect a compatible profile, explain any data-format upgrade and backup prerequisites, and enter it after successful validation. Do not send returning users through first-time setup again. Unsupported/newer data formats receive an explanation and safe exit/export options available under that architecture.

### 13.3 Connectivity and save-state vocabulary

Personal-only local activity should not be accompanied by a perpetual warning that the internet is unavailable. If no current task needs connectivity, no banner is necessary. A local save is complete only after the future local persistence layer confirms it; a queued collaboration change is not a confirmed shared result.

| Future condition                   | Proposed wording/action                                                              | Architectural limit                                                          |
| ---------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------------------------------------------------- |
| Personal data committed locally    | “Saved on this device” where useful                                                  | Does not imply backed up, encrypted or copied to another device              |
| Offline, local task available      | Continue normally                                                                    | Do not disable personal tracking merely because internet is absent           |
| Group read from approved cache     | “Last updated [time]. Connect to refresh.”                                           | Only if retention/revocation policy permits cached access                    |
| Group write requires online access | “Connect to record this group change” with Retry                                     | Recommended safe provisional default; no speculative group queue             |
| Approved offline group draft       | “Saved draft on this device”                                                         | Not shared, not confirmed membership, not a settled balance                  |
| Queue exists after future approval | “Waiting to send” → “Sending” → “Confirmed by service”                               | Durable identity, replay, authorization and acknowledgement must exist first |
| Rejected or revoked access         | Explain rejected change and available private recovery/export options                | Do not continuously retry against lost permission                            |
| Conflict requires review           | “This source changed. Review before continuing.”                                     | Never silently merge money, immutable versions or recipient confirmation     |
| Storage full/locked/corrupt        | “Could not save on this device,” preserve recoverable input and offer valid recovery | No success toast; actual platform error determines permitted actions         |

Default recommendation: personal data remains device-local; online Shared expenses uses server-confirmed authority; offline group writes remain disabled until a durable queue and conflict policy are approved. This is a provisional safety/clarity default, not a selected backend. Do not implement status banners, local persistence or this group policy in current V3.

### 13.4 Backup, migration and privacy dependencies

Before native restore is specified as implementation-ready, decide whether a backup contains attachment bytes, operational evidence, encryption keys, group links or only private graph records; whether it creates a new profile or replaces one; and how old V3 exports are validated. Current trusted server provenance and shared-history guarantees cannot be assumed to work unchanged on an unrelated offline device.

Local profile deletion, remote group membership removal, online account deletion and removal of a backup copy are different actions. Show their actual scope and retention policy separately. Disconnecting does not automatically mean data has disappeared from other devices or participants. Backup encryption and lost-key recovery need a real design before copy promises protection/recovery.

These dependencies affect FUX implementations only. Current color, navigation, responsive layouts, field patterns, review summaries, labels and source-link contracts can be delivered without choosing SQLite, Tauri, Compose, Firebase, another cloud service, or an identity/sync protocol.
