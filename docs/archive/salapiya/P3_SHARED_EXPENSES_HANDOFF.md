## Financial meaning and parity

`src/modules/finance/services/adopt-group-effect.ts`, the V2 sharing services/domain tests and the 40-scenario implementation index remain executable historical references. Native code ports the established algorithm rather than web storage/authentication: UUID participant order, own contribution/share offsets followed by deterministic debtor-creditor matching, separate received refund money and consumption credits, reciprocal source netting, confirmed settlement allocation and separate advances. Suggestions never post or discharge unrelated obligations.

Money crosses boundaries as exact integer minor-unit strings and is calculated with Dart `BigInt` and PostgreSQL integer/numeric arithmetic. Values reject floats, exponential notation, malformed strings and signed-64-bit overflow. Payer totals and consumed-share totals each equal the bill total. Equal PHP100 for three people produces PHP33.34/33.33/33.33 in canonical participant order. Current effective revisions contribute once; prior revisions and actor-attributed decisions remain immutable.

The canonical PHP1,200 purchase conversion retains its original action and one PHP1,200 outgoing movement, with PHP400 expense and PHP800 receivable. Another participant's private ledger is never posted by group acceptance. New private refund/clearing recipes use `sharedAccounting: "2"` to offset existing receivable/payable buckets in the inherited order. Missing/version-1 recipes retain their original deterministic plans when replayed; this does not rewrite accepted financial history. Unpaid share credits reduce existing payables. Restoring clearing reverses the exact prior noncash classification and preserves cash.

Actual payment money can be recorded independently of recipient confirmation. It enters private clearing, with no expense. Explicit clearing requires a confirmed report, no advance, and complete adopted source coverage. A reversed group report never invents a cash refund: explicit restore-clearing retains the actual payment. Reassignment is allowed only for closed/cancelled reports with the same group, parties, date, account and amount, after dependent clearing was restored. It replaces the same private action instead of posting cash again.

Refund money without adopted coverage remains in private clearing. Adopting the source later permits explicit reclassification with the same refund date/account/cash. Corrections do not overwrite private evidence. Users can retain their accepted source with an attributed review reason; `p3_private_review` records this without advancing the financial revision.

`card_funding_contract.dart` validates an existing immutable owner/card-purchase reference and classifies consumption/receivable with zero additional cash or card liability. Canonical executable fixtures cover this boundary, including zero consumption. There is no production native card posting adapter in P3. P4 owns actual card balances, purchases, corrections and refunds; the native card path fails closed. Scenario 31 is a P4 dependency, not a native pass.

## Authority, schema and privacy

Only new migrations `20261025000700` through `20261025001900`, plus `20261026002000`, extend PostgreSQL. Existing web/P0/P2 migrations are preserved. Each deployment used the existing project verifier and a CLI dry run showing exactly the outstanding migration names before application to `salapiya-dev` in Tokyo (`uxnyxhwqshqpvinvopiv`). Migration 020 fixes the actor-scoped original-receipt lookup discovered by the native old-archive recovery test; its local and hosted foreign-owner regressions pass.

- Private `salapiya_p3` contains authoritative bounded group documents, immutable command receipts, invitation hashes and immutable event evidence. Commands serialize the group, authenticate the current provider session, recheck current role/creator/recipient/membership and expected source versions, and validate money/capacity. Rejections commit only their immutable receipt, without partial financial/group effects.
- `p3_submit_command` binds command identity to the authenticated actor and frozen payload. Same ID/same payload returns the original receipt; changed payload is rejected. Group administration cannot confer private financial authority.
- Public `p3_group`, `p3_resource` and `p3_private_review` expose sanitized owner-specific projections, with forced SELECT RLS and explicit SELECT-only grants to authenticated clients. RPCs remain the mutation boundary. No broad direct financial/group write grants are introduced.
- SQL immutable-source validation independently checks bill revision/refund prefixes, totals, caps and settlement terms. The server computes private posting plans; uploaded client plans are not trusted.
- Invitations use 256 random bits, SHA256 hash-only server storage, seven-day expiry, revocation and single use. The intended email must match the authenticated verified identity. Acceptance requires explicit history-visibility consent. Manual claims require owner nomination and review at the unchanged group version; no display-name identity matching or public directory exists. Historical manual confirmations remain labeled unverified after a claim.
- Removal/exit closes membership and prevents new writes at acceptance time, including previously queued offline work. Entitled bills and relevant later corrections/receipt resolution remain available, while unrelated future bills/activity are excluded. Former documents are incomplete and hide the live global version. Owner loss freezes/archive administration; no automatic peer takeover is implemented. The provider deletion adapter reacts to an actual deleted auth identity; tests use the local PostgreSQL engine, not deletion of hosted Google/test users.

PowerSync privacy is independent of Supabase RLS. `sync-streams.yaml` uses authenticated `auth.user_id()` to filter owner-specific group metadata/resources and private reviews; no client-controlled membership parameter grants access. The existing restricted replication role and publication are extended with SELECT on the projection tables. Private accounts, balances, funding selections, profile journals of other owners, invitation secrets and recovery material are never group stream payloads.

Migration 018 keeps full sanitized `p3_group.document` for authenticated API/private validators, while CDC selects `sync_document AS document` plus independently versioned bill/settlement/activity resources. Unchanged resources do not advance or resend because an unrelated bill changed. Metadata includes audience version, exact resource count and SHA256 digest over canonical ordered resource IDs/versions/payload digests. `shared_snapshots.dart` assembles an encrypted local cache only when all these match in a consistent SQLite transaction. Partial/mixed download generations preserve the prior coherent snapshot. A successful Sync now also requires a fresh authenticated group boundary and matching downloaded coverage, alongside the original private financial boundary.

## Offline storage and recovery

Issued invitations can be selected for revocation by their recorded issuance/reference; owners do not have to discover an internal ID. A corrected integrated-purchase group draft carries its original private-purchase link forward. If that private source changed or was already adopted elsewhere, adoption fails closed for explicit Money-history review rather than offering another automatic cash posting. The final four-theme/platform widget pass covers these states.

Rejected bill/payment work has an inspectable original-input review. A user can create a separately identified corrected draft using current participants/sources; the rejected command and receipt remain immutable. This does not retry a changed payload under an old ID or silently post private money. Accepted retained-evidence reasons are visible in Private review; archived review copies are labeled historical and do not suppress current review. New refunds affecting the adopter's own axes request review again unless they have adopted coverage or a current matching retained-evidence decision.

SQLite local schema is version 4; connected storage retains version 2; shared storage is version 3. The transactional P2 upgrade rebuilds only the journal leaf to admit shared ledgers, preserving exact IDs, foreign keys, seals and amounts. It never disables foreign keys or replays web SQL into SQLite. Interrupted migration rolls back. Existing full downloaded P3 history seeds the new cache during offline upgrade.

`shared_intent` freezes the original command/actor/group/payload and retains pending, accepted, reconciled, review and restored states. SDK insert-only `p3_transport` uses the existing durable P2 connector. Network/provider failures retain the queue. Accepted receipts remain pending reconciliation until their facts appear in a coherent entitled cache; a receipt alone does not create an accepted visible balance. Rejected work stays reviewable and does not stall independent commands. Corrections, invitations, membership administration and capacity-sensitive resolution require online review. Ordinary bill/payment reporting can be captured offline against downloaded sources, with current authority rechecked by the server.

Private backup format 3 extends compatible formats 1/2 with original group intents, drafts and historical private reviews. Existing accepted private financial records and source links remain intact. Archives contain neither group write authority nor invitation secrets/tokens. Restored intents are held until current authentication and original receipt lookup; a missing receipt requires explicit same-ID resume under current authorization. Old backups cannot overwrite newer accepted group facts. Group-history JSON clipboard export is a sanitized entitled historical export, separate from a restorable private profile archive. Packaged invitation deep links are not registered; manual code entry is functional.
